For this project, I was mostly responsible for designing and implementing the card and battle systems used throughout gameplay.

I developed systems for deck drawing, card management, runtime data handling, and class-based gameplay behaviors using ScriptableObjects and modular C# architecture.

DeckDraw System

DeckDraw acts as the central deck manager that controls the player’s active deck during gameplay.

1. Loading Player Class Data

When a match starts, DeckDraw reads the player’s save data to determine which character class the player selected, such as Knight or Chemist. This lets the system automatically load the correct starting cards for that class.

2. Reading ScriptableObject Card Data

Each card is defined as a ScriptableObject containing the card name, sprite, and description text. DeckDraw processes these ScriptableObjects from the starting deck array to build the in-match deck.

3. Runtime Dictionaries

To make UI lookups faster, DeckDraw stores card information in dictionaries. One dictionary maps card names to sprites, while another maps card names to description text.

4. Random Card Drawing

At the start of each turn, DeckDraw randomly selects five cards from the deck list. These card names are then passed to AssignCard, which displays the correct card sprite and description.

5. Calling Card Actions by Name

Each character class has its own action script that inherits from a shared base Cards class. AssignCard uses the card name provided by DeckDraw to call the correct gameplay function through a card-action dictionary built on startup.

AssignCard Script Breakdown

AssignCard.cs

Purpose

AssignCard controls how each card slot displays card information and connects player input to the correct gameplay function.

How It Works

  • Receives card names from DeckDraw after the deck is shuffled and cards are selected.
  • Uses dictionaries to match card names with sprites, descriptions, and gameplay actions.
  • Updates the card UI so the player sees the correct image and description.
  • Checks player input, energy cost, and battle state before allowing a card action to run.
  • Calls the correct class-specific function, such as Knight, Chemist, or Wizard card behavior.

Why I Built It This Way

This structure made the card system easier to expand because new cards could be added without rewriting the entire UI system. It also separated card data from card behavior, making the system cleaner for designers and programmers. 


using UnityEngine;
using UnityEngine.UI;
using System.Collections;
using Unity.VisualScripting;

// Handles the assignment and functionality of individual cards in the UI.
// Works with DeckDraw to assign cards, trigger actions, and manage card usage.
public class AssignCard : MonoBehaviour
{
    public string cardNameFromList;
    public Button cardButton;
    public bool cardUsed;
    public Image cardImage;

    private BattleSystem BSystem;
    private DeckDraw cardDraw;
    private EnergySystem energy;

    public void SetupCardButton()
    {
        cardImage.enabled = true;
        cardImage.sprite = cardDraw.allPossibleSprites[cardNameFromList];

        cardButton.onClick.RemoveAllListeners();
        cardButton.onClick.AddListener(OnCardClicked);
        cardButton.interactable = true;
    }

    private void OnCardClicked()
    {
        switch (cardDraw.characterClass)
        {
            case CharacterClass.KNIGHT:
                // Check energy, invoke matching card action,
                // then discard and reset the card.
                break;

            case CharacterClass.CHEMIST:
                // Run Chemist card behavior.
                break;

            case CharacterClass.WIZZARD:
                // Run Wizard card behavior.
                break;
        }
    }

    public IEnumerator AssignNewCard(string newCardName)
    {
        yield return new WaitForSeconds(.15f);

        cardNameFromList = newCardName;
        cardUsed = false;

        SetupCardButton();
    }
}
