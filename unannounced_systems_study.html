Study Goals

  • Separate reusable definitions from runtime state.
  • Give each player an independent objective instance.
  • Keep important decisions authoritative.
  • Drive UI from gameplay state instead of duplicating logic.

System Architecture

A compact separation between static data, live state, server decisions, and presentation.

Definition Data

Designer-authored data describes an objective's name, duration, requirements, and reward. It is treated as a reusable definition rather than modified during play.

Runtime Instance

Starting an objective creates a unique runtime record containing its owner, progress, status, identifier, and timing data.

Authoritative Manager

A server-side manager validates requests and changes runtime state. Clients display the resulting state but do not decide whether an objective succeeds or fails.

Player UI

The interface receives state updates for the local player and displays progress and time remaining without maintaining a second version of the gameplay rules.

Player-Specific Runtime State

This independently written example demonstrates how one reusable definition can produce separate live instances for different players.

PortfolioObjectiveTypes.h — recreated example

Purpose

Store only the information that changes while an objective is active. A definition key identifies the reusable design data, while a unique instance ID identifies this particular run. 

enum class EObjectiveStatus : uint8
{
    Active,
    Completed,
    Failed
};

struct FObjectiveRuntimeState
{
    FGuid InstanceId;
    FName DefinitionKey;
    TWeakObjectPtr<APlayerState> Owner;
    EObjectiveStatus Status = EObjectiveStatus::Active;
    int32 CurrentProgress = 0;
    int32 RequiredProgress = 0;
    double EndTimeSeconds = 0.0;
};

Independent Player Timers

Each runtime instance stores an authoritative end time. This prevents two players who begin at different moments from accidentally sharing the same countdown.

PortfolioObjectiveManager.cpp — recreated example 
bool APortfolioObjectiveManager::StartObjective(
    APlayerState* Player,
    FName DefinitionKey,
    float DurationSeconds)
{
    if (!HasAuthority() || !IsValid(Player))
    {
        return false;
    }

    FObjectiveRuntimeState NewState;
    NewState.InstanceId = FGuid::NewGuid();
    NewState.DefinitionKey = DefinitionKey;
    NewState.Owner = Player;
    NewState.EndTimeSeconds =
        GetWorld()->GetGameState()->GetServerWorldTimeSeconds()
        + DurationSeconds;

    ActiveObjectives.Add(NewState.InstanceId, MoveTemp(NewState));
    return true;
}

Why an end time?

Clients can calculate a display value from synchronized server time. The server still owns expiration, while the UI can update smoothly without sending a replicated value every frame.

UI Synchronization

The widget presents authoritative state instead of running a separate gameplay timer.

Display Flow

  • The local player receives the relevant runtime state.
  • The widget calculates time remaining from the replicated end time.
  • Progress events update the displayed count.
  • A terminal status hides the active display and shows the appropriate feedback.
  • The server remains responsible for completion and failure decisions.

Authority and Validation

Server Responsibilities

  • Create runtime instances
  • Validate ownership
  • Accept progress
  • Resolve expiration

Client Responsibilities

  • Send requests
  • Display local state
  • Animate feedback
  • Never decide success

What I Learned

  • Runtime instances need unique identities separate from reusable definition data.
  • Player ownership should be explicit in multiplayer gameplay state.
  • Gameplay timers and UI timers should not compete as separate sources of truth.
  • Server time allows responsive countdown displays without replicating every tick.
  • Small, focused systems are easier to test than tightly coupled manager and widget logic.
