System Architecture

Separating reusable mission definitions from player-owned runtime instances.

Definition Data

Designer-authored Data Assets describe a mission's name, duration, requirements, and reward. It is treated as a reusable definition rather than modified during play.

Runtime Instance

Starting a mission creates a unique runtime record containing its owner, progress, status, identifier, and timing data.

Authoritative Manager

The Mission Manager validates requests and changes runtime state. Clients display the resulting state but do not decide whether a mission succeeds or fails.

Player UI

The interface receives state updates for the local player and displays progress and time remaining without maintaining a second version of the gameplay rules.

Player-Specific Runtime State

One reusable mission definition can produce separate live instances for different players.

MissionManager.h — Runtime Mission State

Purpose

Each active mission is represented by an independent runtime instance. DefinitionId identifies the reusable Data Asset definition, while InstanceId uniquely identifies a particular player’s active mission. The runtime state tracks ownership, requirements, status, modifiers, and timing information.

MissionManager.cpp — Creating a Player-Owned Mission

When a player starts a mission, the server creates a unique runtime instance from designer-authored mission data. Modifiers and package requirements are copied into live state, and the resulting instance is associated with the owning PlayerState. 


FMissionRuntimeState RuntimeMission;
RuntimeMission.InstanceId = FGuid::NewGuid();
RuntimeMission.DefinitionId = DefinitionId;
RuntimeMission.OwningPlayerState = OwningPlayerState;

if (MissionDefinition)
{
    if (const FMissionModifier* Modifier = MissionDefinition->FindModifier(EMissionModifier::MissionTimed))
    {
        RuntimeMission.bIsTimed = true;
        RuntimeMission.TimeLimit = FMath::Max(0.0f, Modifier->Value);
    }

    for (const FMissionPackageOption& Option :
         MissionDefinition->PackageOptions)
    {
        FMissionRequirement& NewRequirement = RuntimeMission.Requirements.AddDefaulted_GetRef();

        NewRequirement.PackageTypeReq = Option;
        NewRequirement.RequiredCount = Option.PackageCount;
        NewRequirement.DeliveredCount = 0;
    }

    RuntimeMission.bFailOnDestroyed =
        MissionDefinition->HasModifier(EMissionModifier::FailOnVehicleDestroyed);
}

const FGuid MissionInstanceId = RuntimeMission.InstanceId;

RuntimeMissions.Add(MissionInstanceId, MoveTemp(RuntimeMission));

FPlayerActiveMission& PlayerMissions = PlayerActiveMissions.FindOrAdd(OwningPlayerState);

PlayerMissions.MissionInstanceIDs.AddUnique(MissionInstanceId);

Independent Timer Setup

Each timed mission owns a separate timer handle. The bound delegate includes the unique mission instance ID, ensuring expiration affects the correct player-owned mission. 

FMissionRuntimeState* StartedMission =
    RuntimeMissions.Find(MissionInstanceId);

if (StartedMission &&
    StartedMission->bIsTimed &&
    StartedMission->TimeLimit > 0.0f)
{
    StartedMission->EndServerTime =
        GetWorld()->GetGameState()->GetServerWorldTimeSeconds() + StartedMission->TimeLimit;

    FTimerDelegate TimeoutDelegate;
    TimeoutDelegate.BindUObject(this ,&AMissionManager::HandleMissionTimerExpired, MissionInstanceId);

    GetWorldTimerManager().SetTimer(StartedMission->MissionTimerHandle, TimeoutDelegate, StartedMission->TimeLimit, false);
}

The synchronized server end time gives the owning player's UI a stable countdown value, while mission expiration remains controlled by the server-side Mission Manager.

Package & Warehouse Systems

Connecting reusable world objects to mission requirements and inventory interactions.

Runtime Package Identity

Physical packages receive unique runtime identities while retaining reusable definition data. This supports tracking individual objects as they move between the warehouse, player, vehicle inventory, and delivery destination.

Mission Evaluation

Missions evaluate delivered package characteristics against their requirements instead of relying on a single hard-coded object, allowing the same world systems to support multiple jobs.

Reusable Spawning

I worked on distributing package variations through warehouse spawn locations and reusing actors through pooling. Spawn reservations help avoid multiple packages occupying the same space.

MissionManager.cpp — Evaluating Delivered Packages

Requirement Matching

Delivered package data is checked against the first compatible incomplete requirement. The mission completes only after every required category reaches its target quantity. 

bool AMissionManager::DoesPackageMatchRequirement(
    const UPackageData* PackageData,
    const FMissionPackageOption& Requirement) const
{
    if (!IsValid(PackageData))
    {
        return false;
    }

    if (Requirement.RequirementType == EPackageRequirementType::Anything)
    {
        return true;
    }

    return PackageData->PackageShape == Requirement.PackageShape &&
           PackageData->PackageAttribute == Requirement.PackageAttribute;
}

bool AMissionManager::ApplyPackageDataToMission(
    FMissionRuntimeState& RuntimeMission,
    const UPackageData* PackageData)
{
    for (FMissionRequirement& Progress : RuntimeMission.Requirements)
    {
        if (Progress.DeliveredCount >= Progress.RequiredCount)
        {
            continue;
        }

        if (!DoesPackageMatchRequirement(PackageData, Progress.PackageTypeReq))
        {
            continue;
        }

        ++Progress.DeliveredCount;

        if (AreAllRequirementsComplete(RuntimeMission))
        {
            CompleteMission(RuntimeMission);
        }

        return true;
    }

    return false;
}

Warehouse.cpp — Creating Runtime Package Data

Definition Data vs. Runtime Identity

The warehouse duplicates reusable package definition data for each physical actor. Every package receives its own inventory identity without modifying the original Data Asset. 

UPackageData* AWarehouse::BuildRuntimePackageData(
    APackageActor* Package) const
{
    if (!IsValid(Package))
    {
        return nullptr;
    }

    const UPackageData* SelectedDefinition = SelectPackageDefinition();

    if (!IsValid(SelectedDefinition))
    {
        SelectedDefinition = Package->PackageData;
    }

    if (!IsValid(SelectedDefinition))
    {
        return nullptr;
    }

    UPackageData* RuntimeData =
        DuplicateObject<UPackageData>(SelectedDefinition, Package);

    if (!RuntimeData)
    {
        return nullptr;
    }

    RuntimeData->PackageID = FInventoryItemID(FGuid::NewGuid());

    RuntimeData->MissionInstanceId.Invalidate();
    RuntimeData->AssignedDestinationName = NAME_None;

    if (RuntimeData->PackageGridCoords.IsEmpty())
    {
        RuntimeData->PackageGridCoords.Add(FGridCoord());
    }

    return RuntimeData;
}

UI Synchronization

The widget presents authoritative state instead of running a separate gameplay timer.

Display Flow

  • The local player receives the relevant runtime state.
  • The widget calculates time remaining from the replicated end time.
  • Progress events update the displayed count.
  • A terminal status hides the active display and shows the appropriate feedback.
  • The server remains responsible for completion and failure decisions.

Player-Specific Timer Demonstration

This demonstration shows two players starting missions at different times. Each player receives an independent countdown connected to their own runtime mission instance, preventing one player's timer from overwriting or resetting the other player's display.

The Mission Manager maintains the authoritative timing state, while each player's UI retrieves and displays the time associated with their active mission. Mission expiration and failure are determined by gameplay logic rather than by the widget.

What I Learned

  • Runtime instances need unique identities separate from reusable definition data.
  • Player ownership should be explicit in multiplayer gameplay state.
  • Gameplay timers and UI timers should not compete as separate sources of truth.
  • Server time allows responsive countdown displays without replicating every tick.
  • Small, focused systems are easier to test than tightly coupled manager and widget logic.
