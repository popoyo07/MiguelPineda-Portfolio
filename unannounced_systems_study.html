System Architecture

Separating reusable mission definitions from player-owned runtime instances.

Definition Data

Designer-authored Data Assets describe a mission's name, duration, requirements, and reward. It is treated as a reusable definition rather than modified during play.

Runtime Instance

Starting a mission creates a unique runtime record containing its owner, progress, status, identifier, and timing data.

Authoritative Manager

The Mission Manager validates requests and changes runtime state. Clients display the resulting state but do not decide whether a mission succeeds or fails.

Player UI

The interface receives state updates for the local player and displays progress and time remaining without maintaining a second version of the gameplay rules.

Player-Specific Runtime State

One reusable mission definition can produce separate live instances for different players.

Purpose

Store only the information that changes while a mission is active. A definition key identifies the reusable design data, while a unique instance ID identifies this particular run. This temporary example will be replaced with an approved excerpt from the production code. 

enum class EObjectiveStatus : uint8
{
    Active,
    Completed,
    Failed
};

struct FObjectiveRuntimeState
{
    FGuid InstanceId;
    FName DefinitionKey;
    TWeakObjectPtr<APlayerState> Owner;
    EObjectiveStatus Status = EObjectiveStatus::Active;
    int32 CurrentProgress = 0;
    int32 RequiredProgress = 0;
    double EndTimeSeconds = 0.0;
};

Independent Player Timers

Each runtime instance has independent timing state so players can begin at different moments.

Starting a timed runtime instance — illustrative placeholder

This temporary example demonstrates the concept and will be replaced with a short, approved production excerpt. 

bool APortfolioObjectiveManager::StartObjective(
    APlayerState* Player,
    FName DefinitionKey,
    float DurationSeconds)
{
    if (!HasAuthority() || !IsValid(Player))
    {
        return false;
    }

    FObjectiveRuntimeState NewState;
    NewState.InstanceId = FGuid::NewGuid();
    NewState.DefinitionKey = DefinitionKey;
    NewState.Owner = Player;
    NewState.EndTimeSeconds =
        GetWorld()->GetGameState()->GetServerWorldTimeSeconds()
        + DurationSeconds;

    ActiveObjectives.Add(NewState.InstanceId, MoveTemp(NewState));
    return true;
}

Why an end time?

Clients can calculate a display value from synchronized server time. The server still owns expiration, while the UI can update smoothly without sending a replicated value every frame.

Package & Warehouse Systems

Connecting reusable world objects to mission requirements and inventory interactions.

Runtime Package Identity

Physical packages receive unique runtime identities while retaining reusable definition data. This supports tracking individual objects as they move between the warehouse, player, vehicle inventory, and delivery destination.

Mission Evaluation

Missions evaluate delivered package characteristics against their requirements instead of relying on a single hard-coded object, allowing the same world systems to support multiple jobs.

Reusable Spawning

I worked on distributing package variations through warehouse spawn locations and reusing actors through pooling. Spawn reservations help avoid multiple packages occupying the same space.

UI Synchronization

The widget presents authoritative state instead of running a separate gameplay timer.

Display Flow

  • The local player receives the relevant runtime state.
  • The widget calculates time remaining from the replicated end time.
  • Progress events update the displayed count.
  • A terminal status hides the active display and shows the appropriate feedback.
  • The server remains responsible for completion and failure decisions.

Player-Specific Timer Demonstration

This demonstration shows two players starting missions at different times. Each player receives an independent countdown connected to their own runtime mission instance, preventing one player's timer from overwriting or resetting the other player's display.

The Mission Manager maintains the authoritative timing state, while each player's UI retrieves and displays the time associated with their active mission. Mission expiration and failure are determined by gameplay logic rather than by the widget.

What I Learned

  • Runtime instances need unique identities separate from reusable definition data.
  • Player ownership should be explicit in multiplayer gameplay state.
  • Gameplay timers and UI timers should not compete as separate sources of truth.
  • Server time allows responsive countdown displays without replicating every tick.
  • Small, focused systems are easier to test than tightly coupled manager and widget logic.
